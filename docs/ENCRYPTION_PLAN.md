# Encryption and key-management plan

Meat2D should treat encryption as a confidentiality feature for selected
payloads, not as a way to make a shipped game impossible to inspect. Any key
embedded in a client can eventually be extracted by the person running that
client. Public game configuration, shaders, executable code, and ordinary
client assets should therefore remain unencrypted unless the goal is modest
obfuscation.

## Recommended construction

Use a vetted cryptographic library behind a small engine interface. The
preferred candidate is libsodium's XChaCha20-Poly1305-IETF AEAD construction:

- 256-bit keys and 192-bit nonces;
- authenticated encryption, so tampering fails before plaintext is consumed;
- associated data (AAD) for package metadata that should be authenticated but
  not hidden;
- random nonces are safe for this construction when generated by a secure RNG.

See the [libsodium AEAD documentation](https://libsodium.gitbook.io/doc/secret-key_cryptography/aead)
and [XChaCha20-Poly1305 guidance](https://libsodium.gitbook.io/doc/secret-key_cryptography/aead/chacha20-poly1305/xchacha20-poly1305_construction).

OpenSSL EVP is a valid alternative for applications that already require
OpenSSL, FIPS provider workflows, or broad interoperability. It should be
wrapped in the same engine interface; callers should use an AEAD mode such as
AES-GCM or ChaCha20-Poly1305, never raw AES, ECB, CBC, or a home-grown cipher.
The [OpenSSL EVP documentation](https://docs.openssl.org/3.4/man3/EVP_EncryptInit/)
requires authenticated decryption to succeed before decrypted output is used.

Do not add encryption by modifying the current FNV checksum. FNV is useful for
accidental-corruption detection in the compression layer, but it is not a
secret, authentication tag, password hash, or signature.

## Package and asset order

The safe package pipeline is:

```text
canonical source bytes
        -> deterministic compression
        -> AEAD encryption for selected entries
        -> signed manifest and package index
```

Compression must happen before encryption because ciphertext is intentionally
incompressible. Each independently addressed entry should carry:

- package format version and encryption algorithm ID;
- key ID, not the key itself;
- random nonce;
- compressed and uncompressed size limits;
- authenticated entry path/type/build ID as AAD;
- ciphertext plus authentication tag;
- optional plaintext hash only when it does not disclose sensitive information.

The manifest should be signed separately with a build-system-held signing key
(for example, Ed25519) and verified using a public key shipped with the
launcher/server. AEAD proves possession of a shared decryption key; it does
not prove that a package came from the engine publisher when that key is also
available to clients.

## Key-management rules

### Developer and build machines

- Never commit keys, passphrases, recovery codes, or decrypted production
  packages.
- Read keys from CI secret storage, an OS keychain, or a hardware-backed
  signing service.
- Keep signing keys separate from encryption keys and rotate by key ID.
- Make reproducible package metadata deterministic, but never make nonces
  deterministic from asset paths or content hashes.

### Servers and multiplayer

- Keep master keys only on the server or a dedicated key-management service.
- Derive scoped per-package, per-user, or per-session keys with a reviewed KDF
  rather than reusing a master key directly.
- Use a real authenticated transport protocol for network sessions; package
  encryption is not a replacement for TLS, DTLS, QUIC, or an equivalent
  authenticated session protocol.
- Reject unknown key IDs, stale package versions, oversized ciphertext, and
  failed tags before decompression or parsing.

### Local saves and user text

- Prefer platform secure storage (Windows DPAPI/Credential Manager, Apple
  Keychain, or a Linux secret-service/keyring) for locally stored keys.
- If a user passphrase is unavoidable, derive a key with Argon2id using a
  random salt and stored parameters. Do not store the passphrase. Libsodium's
  [password-hashing documentation](https://doc.libsodium.org/password_hashing)
  describes this use and warns that passwords should generally not be used as
  encryption keys without a proper derivation step.
- Do not log plaintext, keys, nonces paired with identifying context, or
  decrypted configuration. Clear temporary secret buffers where the platform
  permits it.

## Engine API requirements

Add a codec-neutral `meat2d::security` API only after the dependency and key
ownership boundary is selected. It should:

1. accept spans and explicit maximum sizes;
2. return failure without exposing partially authenticated plaintext;
3. distinguish algorithm/version/key-ID metadata from secret key material;
4. authenticate package metadata through AAD;
5. use the library RNG for nonces and reject caller nonce reuse in managed
   writer APIs;
6. wipe key-owned buffers on destruction where practical;
7. support key rotation and migration without silently downgrading to plaintext;
8. keep encrypted entries independently decryptable for random-access packages.

Tests must include official known-answer vectors, round trips, wrong keys,
wrong AAD, altered nonce/tag/ciphertext, truncation, oversized declarations,
unknown algorithms, key rotation, rollback policy, fuzzing, and interrupted
package writes. Plaintext must not be passed to a parser until tag validation
has succeeded.

## Explicit non-goals

- No custom cipher, XOR scheme, deterministic nonce, or encryption based on a
  content hash.
- No password used directly as an AEAD key.
- No promise that client-shipped encrypted assets are unrecoverable.
- No encryption of data solely to conceal a public format from modders; use
  signatures and documented mod policy for authenticity and compatibility.
